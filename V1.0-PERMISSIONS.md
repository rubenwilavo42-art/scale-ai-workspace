# ScalAI V1.0 — Permissions & Security

## Decisions

ScalAI exposes three user decisions for agent execution:

- **Autoriser une fois** — allows the current action only.
- **Autoriser pour la session** — remembers an allow decision for the current ScalAI session and never persists it to disk.
- **Refuser** — blocks the action.

## Enforcement

The main process owns permission enforcement. Renderer controls are presentation only.

Before an agent process is launched, ScalAI validates that its working directory is inside the active workspace. Missing or invalid workspace roots fail closed.

The launch command is displayed to the user before approval.

## Credentials

Saved credentials never cross the renderer boundary. The existing credential allowlist remains enforced in `session-env.js`: a child process receives only credentials explicitly associated with its declared agent. Unknown/custom commands fail closed and do not inherit provider credentials.

Credential values are never included in permission dialogs, persistence snapshots, logs, or diagnostic errors.

## ACP agents

ACP `session/request_permission` events are normalized to the same three ScalAI choices. A session-level approval is local to the current renderer session and is implemented by reusing the protocol's one-time allow option on matching future requests; ScalAI never grants a provider's permanent/global permission silently.

## Workspace boundary

Agent launches are rejected when their cwd is outside the active workspace. Path normalization is performed in the main process before the check.

## Limitation

For legacy terminal-only CLIs, ScalAI can enforce launch/workspace/credential boundaries but cannot inspect every shell command the CLI itself executes because those commands are inside the agent's PTY. ACP-capable agents provide protocol-level permission events and receive the stronger interactive permission UX above.
